## 1. The Engineering Dilemma: Autonomous Agents on Bare Metal

Modern AI coding agents (such as Claude Code, OpenHands, and Devin) are not passive LLM chat interfaces. They are autonomous Linux execution runtimes. During a single 5-minute task, an agent routinely spawns hundreds of transient bash subshells:
```bash
# Typical microsecond subshells spawned by autonomous agents
bash -c "cargo check --message-format=json 2>&1 | head -n 40"
bash -c "curl -s -X POST https://telemetry.internal/ping -d @state.json"
bash -c "git diff HEAD~1 > /tmp/.patch_cache"
```

To the Linux kernel, these processes often exist for **under 15 milliseconds**.

Traditional observability stacks fail catastrophically here:
1. **Periodic polling (`/proc` scanners every 100ms):** Completely miss subshells that fork, write to disk, open a network socket, and exit between poll intervals.
2. **`auditd` & root-level kernel tracepoints:** Flood system logs (`dmesg`), require `CAP_SYS_ADMIN` root privileges, and impose severe CPU throttling penalties on developer workstations.

We engineered **Agent-Radar** in Rust to solve this dilemma: unprivileged, real-time observability with **flat 0.00% idle CPU overhead**.

### The Epoll Reactor Loop in Rust
Rather than waking up on a timer, Agent-Radar registers interest in file modifications and process lifetimes via Linux `epoll`:

```rust
// File: src/engine/reactor.rs
// Zero-overhead epoll reactor multiplexing inotify masks
use nix::sys::epoll::{epoll_create1, epoll_ctl, epoll_wait, EpollCreateFlags, EpollEvent, EpollOp};
use std::os::unix::io::RawFd;

pub struct KernelReactor {
    epoll_fd: RawFd,
    events: Vec<EpollEvent>,
}

impl KernelReactor {
    pub fn new(capacity: usize) -> Result<Self, std::io::Error> {
        let epoll_fd = epoll_create1(EpollCreateFlags::EPOLL_CLOEXEC)?;
        Ok(Self {
            epoll_fd,
            events: vec![EpollEvent::empty(); capacity],
        })
    }

    /// Blocks indefinitely in kernel space with zero CPU tick until an event arrives
    #[inline(always)]
    pub fn poll_events(&mut self) -> Result<usize, nix::Error> {
        // -1 timeout guarantees 0.00% CPU utilization while idle
        epoll_wait(self.epoll_fd, &mut self.events, -1)
    }
}
```

### Solving the PID Reuse Race Condition
On modern Linux kernels running high-concurrency agent workflows, `/proc/sys/kernel/pid_max` cycles rapidly. If process `14280` writes a file and terminates in 4ms, a subsequent `cargo` invocation might be assigned PID `14280` within milliseconds.

To eliminate false attribution, we correlate the `inotify` event timestamp with the target process's **`starttime` in clock ticks** extracted directly from `/proc/[pid]/stat`:

```rust
// File: src/engine/proc_correlator.rs
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct ProcessIdentity {
    pub pid: i32,
    pub start_time_ticks: u64,
    pub comm: String,
}

impl ProcessIdentity {
    pub fn from_proc(pid: i32) -> Option<Self> {
        let stat_path = format!("/proc/{}/stat", pid);
        let content = std::fs::read_to_string(&stat_path).ok()?;
        
        // Field 22 in /proc/[pid]/stat is starttime (in jiffies after system boot)
        let parts: Vec<&str> = content.split_whitespace().collect();
        let start_time_ticks = parts.get(21)?.parse::<u64>().ok()?;
        let comm = parts.get(1)?.trim_matches('(').trim_matches(')').to_string();

        Some(Self {
            pid,
            start_time_ticks,
            comm,
        })
    }
}
```
